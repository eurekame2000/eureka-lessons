一、为什么你的 clickhouse-mcp-server 需要深度理解 MCP 协议

在 Lesson 02 的骨架中，你硬编码了 tools/call handler，手动解析 JSON-RPC 消息。 这在 demo 阶段没问题，但要构建生产级 server，你需要回答三个问题：

  1. 协议边界：MCP 的 Tool/Resource/Prompt 三者在协议层面的差异是什么？为什么选 Tool 而不是 Resource？
  2. 传输层：MCP 支持 stdio、SSE、WebSocket 三种 Transport。你的 server 在什么场景下用哪种？
  3. 扩展性：后续加一个"list_databases" Resource，需要改动哪些代码？现有架构能否支撑？

这三个问题指向同一个答案：理解 MCP 协议的四层架构。

二、MCP 协议四层架构

MCP (Model Context Protocol) 不是一个简单的"HTTP + JSON"协议，而是一个四层架构：

Layer 4: Application

Tool / Resource / Prompt — AI agent 的能力接口

Tool: 可执行动作（查询、写入、分析）；Resource: 可读取数据（文档、schema）；Prompt: 固定提示模板

Layer 3: Protocol

JSON-RPC 2.0 消息格式 + MCP 定义的 error codes

请求: {jsonrpc, id, method, params}；响应: {id, result/error}；通知: {method, params}（无 id）

Layer 2: Session

连接生命周期管理：initialize → capabilities negotiation → keepalive → shutdown

Client 和 Server 先交换 capabilities（支持哪些 Tool/Resource/Prompt），再开始业务通信

Layer 1: Transport

底层通信方式：stdio、SSE (Server-Sent Events)、WebSocket

stdio: 子进程双向管道（本地最快）；SSE: HTTP 长连接（远程最常见）；WebSocket: 双向实时（低延迟需求）

心智模型：Transport 是"如何连接"，Session 是"如何握手"，Protocol 是"如何说话"，Application 是"能做什么"。 你的 clickhouse-mcp-server 主要关注 Layer 1（Transport 选择）和 Layer 4（工具定义）。

Transport 选择策略

Transport适用场景clickhouse-mcp-server 选型
stdio本地 CLI 工具、VS Code 扩展开发阶段快速验证（同 L02）
SSEHTTP 部署、远程调用生产选型：通过 HTTP 暴露给 AI agent
WebSocket低延迟双向通信、流式结果流式 large query result 时可选
SSE 工作原理 Client 发送 HTTP POST /message 请求，Server 回复 text/event-stream。 每个 MCP 消息是一个 SSE event（event: message\ndata: {json}\n\n）。 Client 可以同时发送多个请求，Server 通过 id 关联 response。

Session 生命周期

三、SDK 选择：Java vs Go

你的 clickhouse-mcp-server 可以用 Java 或 Go 实现。下面是选型对比：

维度Java (spring-ai / langchain4j)Go (mcp-go)

JSON Schema 校验最佳实践

AI agent 可能会生成错误的参数（拼错字段名、传错类型）。必须在校验层拦截，不要等到执行层才报错。

public class ToolSchemaValidator {

    // 使用 NetworkNT JSON Schema 校验器
    private static final JsonSchemaFactory factory =
        JsonSchemaFactory.getInstance(SpecVersion.VariantFlag.V7);

    public ValidationResult validate(String toolName, Map<String, Object> args) {
        JsonSchema schema = getSchemaForTool(toolName);
        JsonNode node = toJsonNode(args);

        Set<ValidationMessage> errors = schema.validate(node);

        if (errors.isEmpty()) {
            return ValidationResult.valid();
        }

        // 将 schema 错误转为用户友好的中文提示
        List<String> friendly = errors.stream()
            .map(e -> toChineseMessage(toolName, e))
            .collect(Collectors.toList());

        return ValidationResult.invalid(friendly);
    }

    private String toChineseMessage(String tool, ValidationMessage msg) {
        if (msg.getKeyword().equals("required")) {
            return String.format("工具 '%s' 缺少必需参数: %s", tool, msg.getArguments().get("missing"));
        }
        if (msg.getKeyword().equals("type")) {
            return String.format("参数类型错误: 期望 %s, 实际 %s",
                msg.getArguments().get("expected"), msg.getArguments().get("found"));
        }
        return msg.getMessage();
    }
}
工具设计原则 (1) 工具名称要动词开头（query, batch_insert, schema） — AI 模型更容易理解；(2) 描述要告诉 agent 何时用、何时不用；(3) required 字段越少越好 — agent 的猜测准确度有限；(4) 用 JSON Schema 的 enum / minimum / maximum 做静态校验。

核心接口

public interface ToolExecutor<T> {

    /**
     * 执行一个工具调用，返回 CompletableFuture
     * 同步工具直接返回 CompletableFuture.completedFuture(result)
     * 异步工具真实编排执行链
     */
    CompletableFuture<ToolResult> execute(ToolContext ctx, Map<String, Object> params);
}

public record ToolResult(
    boolean success,
    Object data,           // 执行结果（JSON 序列化后返回给 agent）
    long durationMs,       // 执行耗时（可观测性）
    String errorMessage,   // 失败时的中文友好错误消息
    String traceId         // 链路追踪 ID（L11）
) {}

public record ToolContext(
    String toolName,
    String traceId,            // 从 MCP 请求头提取的 trace ID
    String parentSpanId,       // 父 span ID 用于链路串联
    Map<String, String> baggage // W3C Baggage: user_id, session_id 等
) {}

工具执行器实现：query

public class QueryExecutor implements ToolExecutor<Void> {

    private final DataSource clickHouseDS;
    private final ObjectMapper jsonMapper;

    public CompletableFuture<ToolResult> execute(ToolContext ctx, Map<String, Object> params) {
        String sql = (String) params.get("sql");
        String format = (String) params.getOrDefault("format", "json");
        int limit = (int) params.getOrDefault("limit", 100);

        long start = System.nanoTime();

        return CompletableFuture
            .supplyAsync(() -> {
                // Step 1: SQL 安全检查（只允许 SELECT）
                validateReadOnly(sql);

                // Step 2: 执行查询
                try (var conn = clickHouseDS.getConnection();
                     var stmt = conn.createStatement()) {
                    stmt.setMaxRows(limit);
                    var rs = stmt.executeQuery(sql);
                    return resultSetToJson(rs);
                }
            }, ExecutorProvider.getClickHousePool())
            .thenApply(json -> {
                long elapsed = (System.nanoTime() - start) / 1_000_000;
                return new ToolResult(true, json, elapsed, null, ctx.traceId());
            })
            .exceptionally(ex -> {
                long elapsed = (System.nanoTime() - start) / 1_000_000;
                return new ToolResult(false, null, elapsed,
                    "查询执行失败: " + toUserFriendlyError(ex),
                    ctx.traceId());
            });
    }

    private void validateReadOnly(String sql) {
        String trimmed = sql.trim().toUpperCase();
        if (!trimmed.startsWith("SELECT")
            && !trimmed.startsWith("SHOW")
            && !trimmed.startsWith("DESCRIBE")
            && !trimmed.startsWith("EXISTS")) {
            throw new IllegalArgumentException(
                "只允许只读查询（SELECT / SHOW / DESCRIBE / EXISTS）。写入请使用 batch_insert 工具。"
            );
        }
    }
}

// batch_insert 执行器 — 复用 Lesson 20 的 BatchImportExecutor
public class BatchInsertExecutor implements ToolExecutor<Void> {

    // 从 L20 引入的写入引擎
    private final BatchImportExecutor batchImporter;

    public BatchInsertExecutor(BatchImportExecutor batchImporter) {
        this.batchImporter = batchImporter;
    }

    public CompletableFuture<ToolResult> execute(ToolContext ctx, Map<String, Object> params) {
        String table = (String) params.get("table");
        List<String> columns = (List<String>) params.get("columns");
        List<List<Object>> rows = (List<List<Object>>) params.get("rows");
        int batchSize = (int) params.getOrDefault("batchSize", 1000);

        long start = System.nanoTime();

        return CompletableFuture
            .supplyAsync(() -> {
                // 直接复用 L20 的 BatchImportExecutor
                BatchResult result = batchImporter.importBatch(
                    BatchRequest.builder()
                        .table(table)
                        .columns(columns)
                        .rows(rows)
                        .batchSize(batchSize)
                        .build()
                );

                return Map.of(
                    "insertedRows", result.insertedRows(),
                    "batchCount", result.batchCount(),
                    "durationMs", result.durationMs(),
                    "errors", result.errors()
                );
            })
            .thenApply(data -> {
                long elapsed = (System.nanoTime() - start) / 1_000_000;
                return new ToolResult(true, data, elapsed, null, ctx.traceId());
            })
            .exceptionally(ex -> new ToolResult(false, null,
                (System.nanoTime() - start) / 1_000_000,
                "批量写入失败: " + toUserFriendlyError(ex),
                ctx.traceId()));
    }
}

超时控制与重试策略

public class RetryableExecutor<T> {

    private final int maxRetries;
    private final long baseDelayMs;

    public RetryableExecutor(int maxRetries, long baseDelayMs) {
        this.maxRetries = maxRetries;
        this.baseDelayMs = baseDelayMs;
    }

    public CompletableFuture<T> executeWithRetry(
            Supplier<CompletableFuture<T>> action,
            Predicate<Throwable> shouldRetry) {

        CompletableFuture<T> future = action.get();
        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            int currentAttempt = attempt;
            future = future
                .exceptionallyCompose(ex -> {
                    if (shouldRetry.test(ex)) {
                        long delay = baseDelayMs * (long) Math.pow(2, currentAttempt);
                        return CompletableFutureUtil
                            .delayedExecutor(delay, TimeUnit.MILLISECONDS)
                            .thenComposeAsync(_unused -> action.get());
                    }
                    return CompletableFuture.failedFuture(ex);
                });
        }
        return future;
    }
}

重试策略要点：

  • 网络超时（SocketTimeoutException）→ 重试，指数退避 100ms/200ms/400ms
  • ClickHouse Replica 临时不可用 → 重试，指数退避 + jitter
  • SQL 语法错误 → 不重试，立即返回给 agent 提示修改 SQL
  • 数据校验失败（重复主键）→ 不重试，返回具体错误行号

线程池隔离

public class ExecutorProvider {

    // 查询线程池：IO 密集型，用较多线程
    private static final ExecutorService clickHousePool =
        new ThreadPoolExecutor(
            10,            // corePoolSize
            50,            // maxPoolSize
            60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(200),
            new ThreadFactoryBuilder().setNameFormat("ch-query-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );

    // 写入线程池：批量操作，复用 L20 的设计
    private static final ExecutorService batchPool =
        new ThreadPoolExecutor(
            4, 20, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(100),
            new ThreadFactoryBuilder().setNameFormat("ch-batch-%d").build(),
            new ThreadPoolExecutor.AbortPolicy()
        );

    public static ExecutorService getClickHousePool() { return clickHousePool; }
    public static ExecutorService getBatchPool() { return batchPool; }
}
面试高频点：线程池隔离 为什么要区分查询和写入两个线程池？因为查询是 IO 密集型（等待 ClickHouse 返回数据），写入是 CPU 密集型（序列化 + 分批）。 混在一起时，大量慢查询可能占满线程池，导致写入任务饿死。用不同的 ThreadPoolExecutor 实现舱壁隔离 (Bulkhead)。

Trace 传播流程

// MCP Server 中 trace 传播流程
//
// AI Agent                    MCP Server                ClickHouse
//    │                            │                        │
//    │ tools/call                 │                        │
//    ├─── jsonrpc request ───────►│                        │
//    │   traceparent: 00-abc-...  │                        │
//    │                            ├─── SELECT ... ───────►│
//    │                            │   traceparent: 00-def │
//    │                            │◄──── result ─────────┤
//    │◄─── jsonrpc response ─────┤                        │
//    │   traceparent: ...        │                        │
//
// 关键: MCP 请求的 traceparent 头部
// 由 MCP Session 层自动提取，注入到 ToolContext
// 执行引擎再透传给 ClickHouse JDBC 驱动的 OpenTelemetry 集成
// Trace 上下文注入到 ClickHouse JDBC
public class TracingConnectionFactory {

    private final Tracer tracer;
    private final DataSource dataSource;

    public Connection getTracedConnection(ToolContext ctx) throws SQLException {
        Connection conn = dataSource.getConnection();

        // 注入 trace context
        Span span = tracer.spanBuilder("clickhouse.query")
            .setParent(TraceContext.fromString(ctx.traceId()))
            .startSpan();

        // 在 MDC 中设置 traceId（L19 TTL/MDC 模式）
        MDC.put("traceId", ctx.traceId());
        MDC.put("spanId", span.getSpanContext().getSpanId());

        // 返回包装后的 Connection
        return new TracedConnection(conn, span, ctx);
    }
}

// 在工具执行器中包装
public CompletableFuture<ToolResult> execute(ToolContext ctx, Map<String, Object> params) {
    // L19 的 TTL MDC 包装器，确保子线程传递 MDC
    return CompletableFuture
        .supplyAsync(
            TtlRunnable.wrap(() -> {
                try (Connection conn = tracingFactory.getTracedConnection(ctx)) {
                    // ... 执行查询
                }
            }),
            executorProvider.getClickHousePool()
        );
}

                    "friendly", "ClickHouse 操作失败: " + shortMessage(ex),
                    "traceId", traceId,
                    "hint", "请检查 ClickHouse 连接状态和查询语法。如需排查，向管理员提供 traceId。"
                )
            )
        );
    }

    private static String shortMessage(Throwable ex) {
        String msg = (ex.getMessage() != null) ? ex.getMessage() : ex.toString();
        if (msg.length() > 200) {
            return msg.substring(0, 200) + "...";
        }
        return msg;
    }
}
错误设计原则 (1) friendly 字段永远使用中文，因为 agent 以中文提问，中文错误的 self-correct 成功率更高； (2) traceId 字段让 agent 在无法处理错误时，能向用户提供排查标识； (3) hint 字段指引 agent 下一步行动（修改 SQL / 检查连接 / 稍后重试）； (4) 底层异常详情（stack trace）记录在日志中，不返回给 agent。

八、面试答法

高频问题 1 "请设计一个可扩展的 Tool Use 系统"

STAR 答法（45秒版本）：

我在设计 clickhouse-mcp-server 时，将一个生产级 Tool Use 系统拆为五个模块：第一，工具注册层基于 MCP 协议标准的 Tool 定义结构，每个工具由 name/description/inputSchema 三元组描述，JSON Schema 做静态参数校验；第二，执行引擎层使用 CompletableFuture 编排异步流程，按工具类型分配到独立的 ThreadPoolExecutor（查询池 / 写入池），实现舱壁隔离；第三，重试和超时层采用指数退避策略，对网络超时等可恢复错误自动重试，SQL 语法错误等不可恢复错误直接返回；第四，可观测性层通过 W3C traceparent 头传播链路上下文，结合 Micrometer + MDC 记录每个工具调用的耗时和结果；第五，错误处理层统一返回中文友好错误消息，附带 traceId 供后续排查。这个架构支持热插拔新工具：只需实现 ToolExecutor 接口 + 注册 JSON Schema，零改动执行引擎。

高频问题 2 "MCP 协议与 OpenAI Function Calling 有什么区别？"

标准答法（40秒版本）：

MCP 和 OpenAI Function Calling 解决相同的问题——让 AI 模型调用外部工具，但设计哲学和协议层次不同。第一，协议边界：OpenAI Function Calling 只是一个 API 参数（functions 数组），而 MCP 是完整协议栈（Transport/Session/Protocol/Application 四层），定义了连接握手、能力协商、生命周期管理；第二，传输层：Function Calling 只能走 HTTP/WebSocket，MCP 还支持 stdio（子进程管道），适合本地桌面应用和 IDE 插件；第三，能力的广度：MCP 定义了 Tool（动作）、Resource（数据）、Prompt（模板）三种能力模型，Function Calling 只有 Function 一个维度；第四，去厂商绑定：MCP 是 Anthropic 开源的开放协议，任何 LLM（Claude/GPT/Gemini）都可实现兼容，而 Function Calling 是 OpenAI 专属。我选择 MCP 构建 clickhouse-mcp-server 的原因是它天生的可观测性和协议规范，未来可以无缝接入不同的 AI agent 客户端。

高频问题 3 "如何保证 Agent Tool 的幂等性和事务性？"

标准答法（35秒版本）：

Tool 幂等性是 Agent 系统中极易被忽略但极为重要的设计点。对于 clickhouse-mcp-server 的三个工具，我采取不同策略：第一，对于 query 工具，它是天然幂等的（SELECT 语句可重复执行），问题不在幂等而在过期性——我在返回数据时附带 ClickHouse 的系统时间戳，让 agent 判断数据是否新鲜；第二，对于 schema 工具，同样天然幂等，我加了 30 秒本地缓存，防止 agent 在同一个对话中频繁调用；第三，对于 batch_insert 工具，它是非幂等的。我的方案是引入请求去重 ID（idempotency key）：agent 在调用时传入 idempotencyKey，server 在 Redis 中缓存已处理的 key 及其结果，重放时直接返回已处理结果。这本质上是分布式事务中的"至多一次"语义保证。

检索练习

不看上方内容，凭记忆回答。答错不扣分，只是帮你定位记忆空白。

1. MCP 协议的四层架构从底层到顶层依次是？

Transport（如何连接）-> Session（如何握手）-> Protocol（如何说话）-> Application（能做什么）。这是 MCP 标准协议分层。

2. 以下哪个场景应该使用 MCP Resource 而不是 Tool？

Resource 用于读取数据（文档、schema、配置），Tool 用于执行动作（查询、写入、分析）。读取 schema 信息天然适合 Resource 模型。但对于 clickhouse-mcp-server，我们用 Tool 封装也有道理——因为需要参数化查询（指定 database/table）。

3. JSON Schema 参数校验中，以下哪项不是最佳实践？

required 字段越少越好。AI agent 的猜测准确度有限，过多的必需参数会让 agent 频繁猜错。应该给每个参数合理的 default 值，只在绝对必要的字段上设 required。

4. 在 clickhouse-mcp-server 的执行引擎中，为什么要区分查询和写入两个线程池？

这是舱壁隔离 (Bulkhead) 模式。查询是 IO 密集型（等待 ClickHouse 返回），写入是 CPU 密集型（序列化 + 分批）。混合时慢查询会占满线程，写入任务饿死。两个独立的 ThreadPoolExecutor + 不同的拒绝策略解决了这个问题。

5. 在 MCP server 中集成链路追踪，trace 上下文通过什么机制传播到 ClickHouse？

MCP 协议使用 W3C traceparent 头传播 trace 上下文。SSE Transport 的 HTTP 请求头中携带 traceparent，MCP Session 层提取后注入 ToolContext，执行引擎通过 OpenTelemetry JDBC 集成（或手动注入）将 trace 传播到 ClickHouse 侧。
