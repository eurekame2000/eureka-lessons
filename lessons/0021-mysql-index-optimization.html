一、B+ 树索引结构：为什么 InnoDB 用 B+ 树不用 B 树/Hash

B+ 树的结构特点

B+ 树是一种平衡多路搜索树，InnoDB 的聚簇索引（主键索引）使用 B+ 树实现。其核心特点：

  • 非叶子节点只存储键值（key）和指针，不存储数据
  • 叶子节点存储完整的行数据（聚簇索引）或主键值（二级索引）
  • 叶子节点之间通过双向链表连接，支持范围查询的高效遍历
  • 所有叶子节点在同一层，保证查询性能稳定（O(log n)）
[B+ 树结构示意]

                    [18, 40]        ← 根节点（非叶子），只存 key
                   /          \
                  /            \
      [5, 10, 15]      [25, 30, 35]  ← 内部节点（非叶子）
       /    |    \        /    |    \
      /     |     \      /     |     \
[1,2,5] [8,10] [12,15] [20,25] [28,30] [32,35,40]  ← 叶子节点，存完整数据
      ←prev────prev────prev────prev────prev────prev→        双向链表连接
      →next────next────next────next────next────next→

为什么不用 B 树？

B 树和 B+ 树的核心区别在于数据存储位置和叶子节点连接：

对比维度B 树B+ 树（InnoDB 选择）
数据存储所有节点都存储数据只有叶子节点存储数据
叶子节点无连接双向链表连接
范围查询需要从根节点多次遍历叶子节点链表遍历，效率高
磁盘 IO非叶子节点占空间大，单次 IO 读取的 key 少非叶子节点只存 key，单次 IO 读取更多 key
查询稳定性数据在不同层，查询路径长度不同所有查询都到叶子节点，路径长度一致
面试要点 InnoDB 选择 B+ 树的核心原因：(1) 磁盘页利用率更高——非叶子节点只存 key，一个 16KB 页可以存更多 key，树高更低（通常 3-4 层可存千万级数据）；(2) 范围查询更高效——叶子节点链表让 WHERE id BETWEEN 10 AND 100 只需定位到 id=10 的叶子节点，然后向右遍历。

为什么不用 Hash 索引？

Hash 索引虽然等值查询是 O(1)，但有几个致命缺陷：

  • 不支持范围查询：WHERE id > 10 无法使用 Hash 索引
  • 不支持排序：Hash 索引的数据是无序的
  • 不支持部分索引匹配：联合索引 (a,b) 无法只使用 a 查询
  • 存在哈希冲突：不同的 key 可能映射到同一个桶

Memory 引擎支持 Hash 索引，但 InnoDB 的 adaptive hash index 是引擎自动管理的，用户无法创建 Hash 索引。

二、联合索引与最左前缀原则

联合索引的结构

联合索引 (a, b, c) 在 B+ 树中的排序规则是：先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。

-- 创建联合索引
CREATE INDEX idx_abc ON t(a, b, c);

-- B+ 树中数据的排序方式
(a=1, b=1, c=1)
(a=1, b=1, c=2)
(a=1, b=2, c=1)  ← b 变化了
(a=1, b=2, c=3)
(a=2, b=1, c=1)  ← a 变化了，b 和 c 重新排序
(a=2, b=1, c=2)
(a=2, b=3, c=1)

-- 查询能命中索引的组合
WHERE a = 1                           -- 命中：使用最左列
WHERE a = 1 AND b = 2                -- 命中：使用 a + b
WHERE a = 1 AND b = 2 AND c = 3      -- 命中：使用 a + b + c
WHERE a = 1 AND c = 3                -- 部分命中：只用到 a
WHERE b = 2                          -- 不命中：跳过了 a
WHERE b = 2 AND c = 3                -- 不命中：跳过了 a

最左前缀原则

最左前缀原则是指：查询条件必须从联合索引的最左列开始，且不能跳过中间的列。

查询条件是否命中索引 (a,b,c)原因
WHERE a = 1命中（用 a）从最左列开始
WHERE a = 1 AND b = 2命中（用 a,b）连续最左前缀
WHERE a = 1 AND b = 2 AND c = 3命中（用 a,b,c）完整前缀
WHERE a = 1 AND c = 3部分命中（只用 a）跳过了 b，c 无法使用索引
WHERE b = 2不命中没有从最左列 a 开始
WHERE b = 2 AND c = 3不命中跳过了 a
WHERE a > 1 AND b = 2部分命中（只用 a）a 用范围查询，b 无法使用索引
WHERE a = 1 AND b > 2 AND c = 3部分命中（用 a,b）b 用范围查询，c 无法使用索引
重要细节 范围查询（>、<、>=、<=、BETWEEN、LIKE 'xxx%'）会使后续的索引列失效。 原因是：范围查询在 B+ 树中定位到一个区间后，区间内 b 的值不是有序的（因为排序是先按 a，再按 b）。

三、覆盖索引：Using index，避免回表

什么是回表？

InnoDB 有两类索引：

  • 聚簇索引（主键索引）：叶子节点存储完整的行数据
  • 二级索引（普通索引）：叶子节点存储索引列的值 + 主键值

当使用二级索引查询时，如果查询列不在索引中，InnoDB 需要：

  1. 通过二级索引找到满足条件的主键值
  2. 用主键值回表到聚簇索引中查找完整的行数据

这个"回到聚簇索引查数据"的过程叫回表，会产生额外的磁盘 IO。

覆盖索引（Covering Index）

如果查询的所有列都包含在索引中，InnoDB 可以直接从索引中返回结果，不需要回表。这就是覆盖索引。

-- 表结构
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    product_id INT,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user_product (user_id, product_id)
);

-- 需要回表：SELECT * 包含 amount 和 created_at，不在索引中
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
-- Extra: Using where（需要回表）

-- 覆盖索引：只查询索引列 user_id 和 product_id
EXPLAIN SELECT user_id, product_id FROM orders WHERE user_id = 100;
-- Extra: Using index（覆盖索引，不需要回表）

-- 扩展索引实现覆盖索引
ALTER TABLE orders DROP INDEX idx_user_product;
CREATE INDEX idx_user_product_amount ON orders(user_id, product_id, amount);

EXPLAIN SELECT user_id, product_id, amount FROM orders WHERE user_id = 100;
-- Extra: Using index（现在 amount 也在索引中了）
优化技巧 如果查询只需要少量字段，且这些字段可以加入索引实现覆盖索引，那么扩展索引列是值得的。 覆盖索引避免了回表，性能提升显著（尤其是磁盘 IO 密集型场景）。 但要注意：索引列越多，索引占用的空间越大，写入时的维护成本也越高。需要在查询性能和写入性能之间权衡。

四、索引下推（ICP，Index Condition Pushdown，MySQL 5.6+）

ICP 解决的问题

在没有 ICP 之前，使用联合索引查询时，存储引擎层只根据索引的最左前缀过滤数据，然后将所有满足条件的行返回给 Server 层，Server 层再应用 WHERE 中的其他条件。

有了 ICP 之后，存储引擎层可以在遍历索引的过程中就应用 WHERE 中的条件，减少回表次数。

-- 示例表
CREATE TABLE employees (
    id INT PRIMARY KEY,
    last_name VARCHAR(50),
    first_name VARCHAR(50),
    birth_date DATE,
    INDEX idx_last_first (last_name, first_name)
);

-- 查询：查找 last_name 以 'A' 开头，且 first_name 以 'B' 开头的员工
EXPLAIN SELECT * FROM employees
WHERE last_name LIKE 'A%' AND first_name LIKE 'B%';

-- 没有 ICP（MySQL 5.5 及之前）：
-- 1. 存储引擎用 last_name LIKE 'A%' 找到所有 last_name 以 A 开头的索引记录
-- 2. 回表读取完整行数据
-- 3. Server 层再过滤 first_name LIKE 'B%'
-- Extra: Using where

-- 有 ICP（MySQL 5.6+）：
-- 1. 存储引擎用 last_name LIKE 'A%' 定位索引范围
-- 2. 在遍历索引时，同时检查 first_name LIKE 'B%'
-- 3. 只有同时满足两个条件的索引记录才回表
-- Extra: Using index condition（ICP 生效）

-- 查看 ICP 是否开启
SHOW VARIABLES LIKE 'optimizer_switch';
-- 应该包含 index_condition_pushdown=on

-- 临时关闭 ICP（用于对比）
SET optimizer_switch = 'index_condition_pushdown=off';

ICP 的生效条件

  • 查询使用联合索引
  • WHERE 条件中，索引的后续列有查询条件（且这些条件不能用于索引查找，只能用于过滤）
  • 查询需要回表（如果是覆盖索引，不需要回表，ICP 无意义）
面试要点 ICP 的全称是 Index Condition Pushdown，它是 MySQL 5.6 引入的优化。 核心思想是：将 WHERE 条件中涉及索引列的判断，从 Server 层"下推"到存储引擎层，在索引遍历阶段就过滤掉不满足条件的记录，减少回表次数。 ICP 对于联合索引的范围查询场景特别有效。

五、EXPLAIN 各字段含义

基本用法

-- 分析一条查询
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 50;

-- 格式化输出（MySQL 8.0+）
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 100;

核心字段解读

type（访问类型，重要）

type 值含义性能
system / const主键或唯一索引等值查询，最多返回一行最好
eq_ref主键或唯一索引连接查询，每行只匹配一行很好
ref普通索引等值查询，可能返回多行良好
range索引范围查询（BETWEEN、IN、>、< 等）一般
index全索引扫描（扫描整个索引树）较差
ALL全表扫描最差
面试高频 type 的性能排序：const > eq_ref > ref > range > index > ALL。 面试时常问："什么时候会出现 ALL？" 答：没有合适的索引、或查询条件无法使用索引时。 优化目标：至少达到 range，理想是 ref 或 const。

Extra（额外信息，重要）

Extra 值含义
Using index覆盖索引，不需要回表
Using index condition使用了索引下推（ICP）
Using whereServer 层需要过滤（可能有回表）
Using filesort需要额外的排序步骤（无法利用索引排序）
Using temporary需要临时表（GROUP BY 无索引、UNION 等）
Using join buffer连接查询使用了 join buffer，可能是索引缺失

其他重要字段

  • key：实际使用的索引名
  • rows：估计需要扫描的行数（越小越好）
  • filtered：表示存储引擎返回的数据在 Server 层过滤后，剩下多少满足查询条件的比例

六、索引失效 7 大场景

即使创建了索引，某些写法也会导致索引失效，变成全表扫描。以下是 7 大常见场景：

1. 对索引列使用函数或计算

-- 索引失效：对索引列使用函数
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- 原因：索引存的是 created_at 的原始值，YEAR() 函数改变了它

-- 修复：改写为范围查询
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

-- 索引失效：对索引列进行计算
EXPLAIN SELECT * FROM products WHERE price * 1.1 > 100;
-- 原因：price * 1.1 不是索引中的原始值

-- 修复：将计算移到等号右边
EXPLAIN SELECT * FROM products WHERE price > 100 / 1.1;

2. 隐式类型转换

-- 假设 phone 是 VARCHAR 类型，有索引
CREATE INDEX idx_phone ON users(phone);

-- 索引失效：字符串列用数字查询，触发隐式转换
EXPLAIN SELECT * FROM users WHERE phone = 13800138000;
-- 原因：MySQL 会把 phone 列的值转成数字再比较

-- 修复：用字符串查询
EXPLAIN SELECT * FROM users WHERE phone = '13800138000';

3. LIKE 左模糊

-- 索引失效：左模糊
EXPLAIN SELECT * FROM users WHERE name LIKE '%明';
-- 原因：B+ 树从左到右排序，'%明' 无法利用排序

-- 索引生效：右模糊
EXPLAIN SELECT * FROM users WHERE name LIKE '张%';
-- 原因：'张%' 可以利用 B+ 树的有序性定位范围

4. OR 连接非索引列

-- 假设只有 user_id 有索引
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR amount > 100;
-- 索引失效：OR 的 amount > 100 部分无法使用索引
-- MySQL 优化器可能选择全表扫描

-- 修复：为 amount 也创建索引，或改写为 UNION
EXPLAIN SELECT * FROM orders WHERE user_id = 100
UNION ALL
SELECT * FROM orders WHERE amount > 100;

5. 使用 != 或 <>

-- 索引可能失效
EXPLAIN SELECT * FROM users WHERE status != 1;
-- 原因：如果 status != 1 的结果占大多数，优化器可能选择全表扫描
-- （因为回表的成本可能比全表扫描还高）

6. 使用 NOT IN

-- 索引可能失效
EXPLAIN SELECT * FROM users WHERE id NOT IN (1, 2, 3);
-- 原因：NOT IN 通常无法利用索引的有序性
-- 修复：改用 NOT EXISTS 或 LEFT JOIN ... WHERE id IS NULL

7. IS NULL / IS NOT NULL（取决于数据分布）

-- 如果 NULL 值很少，索引可能生效
EXPLAIN SELECT * FROM users WHERE email IS NULL;

-- 如果 NULL 值很多，索引可能失效
EXPLAIN SELECT * FROM users WHERE email IS NOT NULL;
-- 原因：优化器会根据数据分布选择成本最低的执行计划
口诀记忆 索引失效 7 字诀：函计隐 OR 不 NOT （函数/计算/隐式转换/OR/!=/左模糊/NOT IN）

七、联合索引排序：ORDER BY + LIMIT 优化

ORDER BY 使用索引的条件

ORDER BY 能使用索引，需要满足以下条件之一：

  • ORDER BY 的列顺序与索引列顺序一致，且方向相同（都是 ASC 或都是 DESC）
  • WHERE 条件使用了索引的最左前缀，ORDER BY 使用了索引的后续列
-- 索引 (a, b, c)

-- 能使用索引排序
EXPLAIN SELECT * FROM t WHERE a = 1 ORDER BY b, c;
-- Extra: Using index condition（索引用于 WHERE + ORDER BY）

-- 不能使用索引排序：b 和 c 的顺序与索引不一致
EXPLAIN SELECT * FROM t WHERE a = 1 ORDER BY c, b;

-- 不能使用索引排序：b 是 ASC，c 是 DESC
EXPLAIN SELECT * FROM t WHERE a = 1 ORDER BY b ASC, c DESC;
-- MySQL 8.0 支持降序索引，可以创建 (a, b, c DESC) 来解决

-- 能使用索引排序：WHERE 命中 a，ORDER BY 命中 b, c
EXPLAIN SELECT * FROM t WHERE a > 1 ORDER BY a, b;
-- 注意：a 用范围查询后，b 能否用于排序取决于 MySQL 版本和优化器

filesort 触发条件

当 ORDER BY 无法使用索引时，MySQL 会进行 filesort（文件排序）。filesort 不是真的用文件排序，而是在内存或临时文件中排序。

filesort 的两种算法 (1) 单路排序：一次性读取所有需要的列到内存，然后排序。需要的内存较大。 (2) 双路排序：先读取排序键和行指针，排序后再回表读取数据。需要两次 IO。 MySQL 会根据 max_length_for_sort_data 和排序数据大小自动选择算法。

ORDER BY + LIMIT 优化

-- 常见慢查询：大偏移量分页
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 100000, 10;
-- 问题：MySQL 需要排序前 100010 行，然后丢弃前 100000 行
-- Extra: Using filesort

-- 优化方案 1：使用覆盖索引 + 延迟关联
EXPLAIN SELECT * FROM orders o
JOIN (SELECT id FROM orders ORDER BY created_at DESC LIMIT 100000, 10) t
ON o.id = t.id;
-- 子查询只查 id（覆盖索引），然后回表拿完整数据

-- 优化方案 2：使用游标分页（最优）
-- 假设上一页最后一条的 created_at = '2024-01-01 10:00:00'，id = 12345
EXPLAIN SELECT * FROM orders
WHERE created_at <= '2024-01-01 10:00:00' AND (created_at < '2024-01-01 10:00:00' OR id < 12345)
ORDER BY created_at DESC, id DESC
LIMIT 10;
-- 利用索引的有序性，直接定位到起始位置

八、慢查询实战：诊断 → 加索引 → EXPLAIN 验证

场景描述

假设你在 clickhouse-mcp-server 项目中有一个 query_log 表，用于记录用户的查询历史。表结构如下：

CREATE TABLE query_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    query_text TEXT,
    query_type VARCHAR(20),
    status VARCHAR(10),
    duration_ms INT,
    created_at DATETIME NOT NULL,
    INDEX idx_user_created (user_id, created_at)
);

-- 慢查询：查询用户 1001 最近 7 天的成功查询，按创建时间倒序，取前 20 条
SELECT id, query_text, duration_ms, created_at
FROM query_log
WHERE user_id = 1001
  AND status = 'success'
  AND created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
ORDER BY created_at DESC
LIMIT 20;

第一步：EXPLAIN 诊断

EXPLAIN SELECT id, query_text, duration_ms, created_at
FROM query_log
WHERE user_id = 1001
  AND status = 'success'
  AND created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
ORDER BY created_at DESC
LIMIT 20;

-- 可能的输出：
-- type: range（使用了 idx_user_created 的 created_at 部分）
-- key: idx_user_created
-- rows: 1500（估计扫描 1500 行）
-- Extra: Using index condition; Using where; Using filesort
-- 问题：
-- 1. Using filesort：ORDER BY created_at DESC 没有用到索引排序（因为 status = 'success' 在中间）
-- 2. Using where：status = 'success' 需要回表后过滤

第二步：分析索引失效原因

  • 索引是 (user_id, created_at)，但查询条件是 user_id = 1001 AND status = 'success' AND created_at >= ...
  • status 不在索引中，导致索引只能用到 user_id，created_at 的范围查询因为 status 在中间而失效
  • ORDER BY created_at DESC 也无法使用索引排序，因为 status 条件打断了索引的连续性

第三步：优化方案

-- 方案 1：扩展索引，包含 status
ALTER TABLE query_log DROP INDEX idx_user_created;
CREATE INDEX idx_user_status_created ON query_log(user_id, status, created_at);

FROM query_log
WHERE user_id = 1001
  AND status = 'success'
  AND created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)

九、ClickHouse 对比：MergeTree 稀疏索引 vs MySQL B+ 树稠密索引

核心差异

ClickHouse 的 MergeTree 引擎使用稀疏索引（Sparse Index），与 MySQL InnoDB 的稠密索引（Dense Index）有本质区别。

对比维度MySQL InnoDB B+ 树ClickHouse MergeTree
索引类型稠密索引（每行都有索引条目）稀疏索引（每隔 N 行一个索引条目）
索引粒度每行默认 8192 行（index_granularity）
适用场景OLTP：高并发点查、事务OLAP：大规模聚合分析
等值查询很快（B+ 树 O(log n)）较慢（需要扫描多个 granule）
范围查询快（叶子节点链表）快（稀疏索引跳过不需要的 granule）
聚合查询慢（需要全表扫描或索引扫描）极快（列存 + 稀疏索引 + 向量化）
写入方式行级写入，实时可见批量写入，后台 merge

稀疏索引的工作原理

-- ClickHouse MergeTree 表的稀疏索引示意

-- 数据按主键排序存储，每 8192 行（一个 granule）生成一个索引条目
-- 索引条目包含：granule 的起始主键值

-- 示例：主键 (user_id, created_at)
-- granule 1: user_id=1, created_at='2024-01-01' ... user_id=1, created_at='2024-01-07'
-- granule 2: user_id=1, created_at='2024-01-08' ... user_id=2, created_at='2024-01-01'
-- ...

-- 查询：WHERE user_id = 1 AND created_at >= '2024-01-05'
-- 1. 稀疏索引快速定位到可能的 granule 范围（granule 1 和 2）
-- 2. 只加载这两个 granule 的数据（其他 granule 跳过）
-- 3. 在 granule 内部再进行精确过滤

-- 对比 MySQL：
-- MySQL 的 B+ 树索引，每个叶子节点对应一行数据
-- ClickHouse 的稀疏索引，每个索引条目对应 8192 行数据
clickhouse-mcp-server 的选型启示 如果你的查询场景是：(1) 按用户 ID 查询最近的查询历史 → MySQL（需要快速点查）；(2) 分析所有用户的查询耗时分布 → ClickHouse（需要大规模聚合）。 这也是为什么 clickhouse-mcp-server 项目有意义：它让你在保留 MySQL 作为 OLTP 存储的同时，利用 ClickHouse 做 OLAP 分析。

十、面试话术

高频问题 1 "MySQL 索引为什么用 B+ 树不用 B 树？"

标准答法（40秒版本）：

MySQL InnoDB 选择 B+ 树作为索引结构，主要有三个原因。第一，磁盘页利用率更高：B+ 树的非叶子节点只存储键值，不存储数据，这样一个 16KB 的磁盘页可以存储更多的键，树的高度通常只有 3-4 层就能存储千万级的数据，减少了磁盘 IO 次数。第二，范围查询更高效：B+ 树的叶子节点通过双向链表连接，执行 WHERE id BETWEEN 10 AND 100 这样的范围查询时，只需要先定位到 id=10 的叶子节点，然后沿着链表向右遍历即可，不需要从根节点重新查找。第三，查询性能稳定：B+ 树的所有查询都必须到达叶子节点，路径长度一致，而 B 树的数据分布在所有层，查询路径长度不固定。这是 InnoDB 选择 B+ 树的核心原因。

高频问题 2 "如何优化一条慢查询？"

STAR 答法（45秒版本）：

我优化慢查询的标准流程分为五步。第一，用 EXPLAIN 分析：查看 type 字段（至少要达到 range，最好是 ref）、key 字段（是否使用了期望的索引）、rows 字段（估计扫描行数）、Extra 字段（是否有 Using filesort 或 Using temporary）。第二，识别索引问题：检查 WHERE 条件是否违反了最左前缀原则、是否有索引失效的场景（函数、隐式转换、左模糊等）、ORDER BY 是否能利用索引排序。第三，调整索引或查询：根据最左前缀原则扩展或调整索引顺序、将范围查询的列放到索引末尾、如果有 filesort 考虑覆盖索引。第四，重新 EXPLAIN 验证：确认 type 提升、rows 减少、Extra 中的 filesort 消失。第五，用实际数据验证性能：用 SHOW PROFILES 对比优化前后的执行时间，确保优化有效。我之前优化过一个 query_log 表的查询，通过扩展索引 (user_id, status, created_at) 避免了 filesort，扫描行数从 1500 降到 200。

高频问题 3 "什么情况下索引会失效？"

标准答法（35秒版本）：

索引失效有七大常见场景，我总结为七个字：函计隐 OR 不 NOT。第一，函数：对索引列使用函数（如 WHERE YEAR(created_at) = 2024），索引存的是原始值，函数改变了它。第二，计算：对索引列进行计算（如 WHERE price * 1.1 > 100），应该把计算移到等号右边。第三，隐式转换：字符串列用数字查询（如 WHERE phone = 13800138000），MySQL 会做类型转换导致索引失效。第四，OR：OR 连接非索引列（如 WHERE user_id = 1 OR amount > 100），可能变成全表扫描。第五，不等于：使用 != 或 <> 通常无法使用索引。第六，左模糊：LIKE '%明' 无法利用 B+ 树的有序性，但 LIKE '张%' 可以。第七，NOT IN：通常无法利用索引。除此之外，覆盖索引可以避免回表，索引下推（ICP）可以减少回表次数，这些都是索引优化的重要手段。

检索练习

不看上方内容，凭记忆回答。答错不扣分，只是帮你定位记忆空白。

1. InnoDB 使用 B+ 树作为索引结构，以下哪个不是其原因？

B+ 树和 B 树都只是索引结构，与事务无关。事务是存储引擎（InnoDB）层面的功能，不是索引结构层面的。A、B、C 都是 InnoDB 选择 B+ 树的正确原因。

2. 对于联合索引 (a, b, c)，以下哪个查询不能命中索引？

B 只能用到 a，c 无法使用索引（跳过了 b）。D 中 b 用范围查询后，c 也无法使用索引。但 B 是完全不能命中（c 完全用不到），而 D 能命中 a 和 b。题目问"不能命中"，单选最优答案是 B（c 完全用不到索引）。

3. 覆盖索引的好处是什么？

覆盖索引是指查询的所有列都包含在索引中，InnoDB 可以直接从索引中返回结果，不需要回表到聚簇索引查找完整数据，从而减少磁盘 IO。覆盖索引的代价是索引变大，写入时的维护成本增加。

4. EXPLAIN 的 type 字段中，以下哪个性能最差？

type 性能排序：const > eq_ref > ref > range > index > ALL。ALL 是全表扫描，性能最差。优化目标：至少达到 range，理想是 ref 或 const。

5. 以下哪个写法会导致索引失效？

对索引列使用函数（YEAR(created_at)）会导致索引失效，因为索引存储的是 created_at 的原始值，YEAR() 函数改变了它。其他写法都可以正常使用索引。
